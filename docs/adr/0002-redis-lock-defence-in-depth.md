# ADR 0002: Redis run lock is defence in depth, not the correctness mechanism

- Status: Accepted
- Date: 2026-10-08

## Context

Several workers may finish steps of the same run at the same moment (parallel branches) and both try to promote the
join step or complete the run; a worker may also try to claim a step of a run whose bookkeeping is in progress. A
distributed lock per run looks like the obvious fix, but a Redis lock (`SET key token NX PX ttl`) is **not a safe
mutual-exclusion primitive on its own**: a process can pause past the TTL (GC, CPU starvation, network partition),
the lock expires, another process acquires it, and both act. Redis replication failover can also lose a lock.

## Decision

Correctness comes from the database:

- claims are compare-and-swap updates on `(Id, Version, Status, LeaseOwner IS NULL)`;
- `StepRun.Version` is a **fencing token**: heartbeats rotate it and a result is only recorded if the worker still
  holds the current value;
- `WorkflowRun.Version` is an optimistic-concurrency token regenerated by every aggregate mutation, so concurrent
  bookkeeping on one run is serialised (the loser reloads and re-applies);
- unique indexes enforce idempotency and one-run-per-schedule-slot.

The Redis lock (`orchestrator:lock:run:{id}`, acquired with `SET NX PX`, released with a Lua compare-and-delete so an
expired holder cannot delete a successor's lock) is taken only around short bookkeeping sections — the claim, recording
an outcome, lease recovery, starting a run — and **never while a handler executes**, so parallel branches still run in
parallel. If it cannot be acquired within `Worker:RunLockWaitTimeout`, recording proceeds anyway; if Redis is down,
acquisition degrades to a no-op handle and a warning is logged.

## Consequences

- The system stays correct with Redis unavailable, slow, or failing over; it only does more optimistic-concurrency
  retries.
- With Redis healthy, contention on hot runs drops (fewer reload/retry cycles, fewer wasted claim attempts).
- Tests run without Redis: `InMemoryDistributedLockProvider` implements the same contract (TTL, token-checked release)
  and is used whenever `Redis:Enabled=false` — suitable for a single instance only.
- A single Redis node is enough; Redlock across several nodes is unnecessary because nothing depends on the lock for safety.
